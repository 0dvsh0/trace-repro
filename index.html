01The problem

Monitoring tools show you where it hurts.
They never show you who hit you.

Modern apps do hundreds of things at once. Payments retry, carts expire, customers click "Pay" — often all on the same order. When two of them collide, the error shows up somewhere else entirely. So your team stares at the wrong place.

Anatomy of a 38-millisecond disaster

  1. 12:04:17.374 Background

    The bank re-sends a payment confirmation

    The same message arrives twice. The order gets updated again — with nothing stopping it.

  2. 12:04:17.386 Background

    A cleanup timer cancels the order

    It thinks the cart was abandoned. At that exact moment, it wasn't.

  3. 12:04:17.412 Customer-facing

    The customer's checkout fails

    They see an error — or worse, get charged twice. This is the only thing that shows up as an error.

Blink of an eye ~100ms
The entire bug 38ms

03How it works

Find it. Prove it. Fix it.

01

Find

It connects the dots.

trace-repro maps every request, background job and database change into a living map. When something breaks, it walks backwards to every event that touched the same record.

FalkorDB · cross-trace graph traversal
02

Prove

It recreates the crash on purpose.

Before touching any code, it writes a test that replays those exact events, in the exact order, milliseconds apart — and watches it fail. The bug is now proven, not guessed.

pytest · GitLab CI · red pipeline
03

Fix

It repairs the root cause.

It follows the map to the code that started the chain reaction, adds the missing safeguard, and reruns the test until it passes. Then it ships the fix to production.

Row lock · idempotency key · Cloud Run

    08Under the hood
    
        
    For the engineers in the room.
    
        
    OpenTelemetry spans and ORM/Redis state mutations stream into FalkorDB. Independent traces are linked through shared (:StateEntity) nodes, and the GitLab Duo Agent queries them via MCP.
    
      
    
      
    
        
    
          
          
          
          
          
          
        
    


    // Execution layer
(:Trace {id, entry_endpoint})
(:Span  {id, start_ns, end_ns, status})

// Stateful entity layer — the bridge between traces
(:StateEntity   {entity_type: "Order", primary_key: "8812"})
(:StateMutation {seq_no, ts_ns, field, old_val, new_val, lock_held: false})

// Code & Git layer
(:ASTFunction {name, file_path, line_range})
(:GitCommit   {sha, mr_iid})

// Causal edges
(:Span)-[:EXECUTED_FUNCTION]->(:ASTFunction)
(:Span)-[:WROTE_ENTITY {ts_ns, delta_json, tx_isolation}]->(:StateEntity)
(:Span)-[:READ_ENTITY  {ts_ns, snapshot_version}]->(:StateEntity)
(:StateMutation)-[:HAPPENED_BEFORE {delta_ms: 38, concurrent_overlap: true}]->(:StateMutation)
    


    // From the crashing span, hop across shared StateEntity nodes to find
// every OTHER independent trace that mutated the same entity before the crash
MATCH (crash_trace:Trace)-[:HAS_SPAN]->(crash_span:Span {id: $crash_span_id})
MATCH (crash_span)-[r_read:READ_ENTITY|WROTE_ENTITY]->(entity:StateEntity)
MATCH (other_trace:Trace)-[:HAS_SPAN]->(mutator_span:Span)-[r_write:WROTE_ENTITY]->(entity)
WHERE other_trace.id <> crash_trace.id
  AND r_write.ts_ns <= r_read.ts_ns
  AND (r_read.ts_ns - r_write.ts_ns) < 60000000000 // 60s causal window
MATCH (mutator_span)-[:EXECUTED_FUNCTION]->(upstream_fn:ASTFunction)
MATCH (crash_span)-[:EXECUTED_FUNCTION]->(crash_fn:ASTFunction)
RETURN
  entity.primary_key AS collided_entity,
  other_trace.entry_endpoint AS interfering_request,
  other_trace.payload_json AS interfering_payload,
  (r_read.ts_ns - r_write.ts_ns) / 1000000.0 AS race_window_ms,
  r_write.lock_held AS was_locked,
  upstream_fn.file_path AS upstream_mutator_file,
  upstream_fn.name AS upstream_mutator_function,
  crash_fn.name AS downstream_crash_symptom
ORDER BY r_write.ts_ns ASC
    


    // Exact chain of state transitions: entity creation → corrupted read.
// Produces the ordered requests, payloads and ms delays for the replay test.
MATCH (entity:StateEntity {primary_key: "8812"})
MATCH (first:StateMutation {seq_no: 0})-[:MUTATED]->(entity)
MATCH (crash:Span {id: $crash_span_id})
MATCH p = shortestPath((first)-[:HAPPENED_BEFORE|CAUSED_READ*..12]->(crash))
UNWIND nodes(p) AS step
OPTIONAL MATCH (s:Span)-[:EMITTED]->(step)
OPTIONAL MATCH (t:Trace)-[:HAS_SPAN]->(s)
RETURN t.entry_endpoint AS request, t.payload_json AS payload,
       step.field AS field, step.old_val AS old_val, step.new_val AS new_val,
       step.ts_ns / 1000000.0 AS ts_ms
ORDER BY ts_ms ASC

import asyncio
import pytest
from tests.repro.harness import Barrier, replay, wallet_credits

@pytest.mark.asyncio
async def test_incident_8812_cross_trace_race(client, worker, seed_order):
    await seed_order(id=8812, status="PENDING", amount=4500)
    barrier = Barrier(parties=3)

    # Causal subgraph: A1 (-38ms) → B2 (-26ms) → C3 (0ms)
    webhook  = replay(client.post, "/webhooks/payment",
                      json={"order_id": 8812, "event": "payment.retry"},
                      barrier=barrier, offset_ms=0)
    expiry   = replay(worker.expire_cart, order_id=8812,
                      barrier=barrier, offset_ms=12)
    checkout = replay(client.post, "/checkout/capture",
                      json={"order_id": 8812}, barrier=barrier, offset_ms=38)

    _, _, res = await asyncio.gather(webhook, expiry, checkout)

    assert res.status_code == 200, res.json()   # RED: 500 InvalidStateError
    assert await wallet_credits(8812) == 1      # no double-credit

    10Questions
    
          
    Good questions.
    Straight answers.
    
        
    
        
    
          
    
            What kind of bugs does it catch?
            
    The nastiest kind: double charges, wrong wallet balances, orders stuck in impossible states. Bugs caused by two things happening at almost the same moment — which are exactly the ones humans struggle to find.
    
          
    
          
    
            Why not just use an AI coding assistant?
            
    They only see the line that crashed, so they patch the symptom. trace-repro proves the cause first with a failing test, then fixes it where it started.
    
          
    
          
    
            Do I have to rebuild my app?
            
    No. A lightweight middleware reports what each request touched. There's no heavy recording, and no need to replay hours of traffic.
    
          
    
          
    
            Will it change code without anyone checking?
            
    It can run fully hands-off, or stop at the merge request for approval. Either way, every fix comes with proof: a test that failed before, passes after, and a before/after map of what changed.
